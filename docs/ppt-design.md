内容形式：每页包含 PPT 展示文字、建议用时和对应讲稿

## 第 1 页：项目概览

建议用时：50 秒

### PPT 展示文字

- mini_code：模块化 Python 编码代理系统
- 核心能力：CLI 交互、模型调用、工具执行、任务管理、团队协作、上下文压缩
- 汇报重点：系统设计 + 模型使用方式 + 模型能力分析

### 讲稿

本项目实现的是一个轻量级编码代理框架，项目名称是 mini_code。它不是一个单纯的大模型聊天程序，而是把模型调用、工具执行、任务状态、后台命令和多代理协作组织成一个完整的工程系统。

从使用角度看，用户可以通过 `mini-code chat` 进入交互式会话，让模型理解开发需求，并根据需要读取文件、执行命令、修改文件或者管理任务。从系统角度看，它更像一个 mini 版的编码代理运行时，负责把模型的推理能力和真实工作区操作连接起来。

本次汇报我会按照项目背景、意义价值、需求描述、概要设计、详细方案、验证结果和应用效果展开。其中重点会放在两个方面：第一，整个项目过程中模型是怎么被使用的；第二，模型在编码代理场景中的能力和边界分别是什么。

## 第 2 页：项目背景

建议用时：1 分钟

### PPT 展示文字

- 大模型具备代码理解、规划和生成能力
- 真实开发任务需要：读写文件、执行命令、跟踪任务、长期上下文
- 单轮问答难以支撑复杂开发流程
- 需要一个可控、可扩展、可验证的代理运行框架

### 讲稿

当前大模型已经具备较强的代码理解和生成能力。例如，它可以解释一段代码的作用，可以根据需求生成函数，也可以分析报错原因。但是在真实开发场景里，只有这些能力还不够。

真实开发任务通常需要连续操作。比如，先阅读项目结构，再定位相关模块，然后修改文件，接着运行测试，最后根据测试结果继续调整。这个过程涉及文件系统、命令执行、状态记录和多轮上下文。如果只是把问题一次性发给模型，模型很难稳定完成整个闭环。

因此，这个项目的背景是：我们希望把大模型从“回答问题的工具”进一步工程化为“能协助完成开发流程的代理”。这就需要一个中间层，也就是代理运行框架。这个框架既要把模型能力接入进来，又要控制模型能做什么、怎么做、做完之后如何验证。

mini_code 正是在这个背景下设计的。它不追求做一个庞大的商业级产品，而是用相对小的代码规模，覆盖编码代理最核心的几个问题：模型调用、工具调用、上下文管理、任务管理和协作机制。

## 第 3 页：意义和价值

建议用时：1 分钟

### PPT 展示文字

- 工程价值：清晰模块边界，便于扩展和测试
- 使用价值：通过 CLI 完成代码代理交互
- 协作价值：支持任务板、子代理、队友线程
- 安全价值：工具执行受工作区路径和危险命令限制
- 研究价值：可观察模型调用、工具选择和上下文管理效果

### 讲稿

这个项目的价值可以从五个角度理解。

第一是工程价值。项目采用 `src` 布局，并且把配置、模型调用、运行时、工具和功能模块拆开。这样后续如果要替换模型提供商、增加工具，或者扩展 CLI 命令，都不需要推翻整个结构。

第二是使用价值。用户可以直接通过命令行和代理交互，不需要自己手动拼接模型请求，也不需要自己维护复杂的消息历史。项目把这些逻辑封装到了运行时中。

第三是协作价值。项目不仅支持单个主代理，还支持子代理和队友线程。队友之间可以通过 inbox 传递消息，也可以从任务板中认领任务。这使它具备了多代理协同的雏形。

第四是安全价值。模型不能直接无限制操作系统。项目中的文件路径会限制在工作区内，`bash` 工具也会拦截一些危险命令，大输出会被截断或落盘，避免大量内容直接塞回上下文。

第五是研究价值。项目记录了模型请求、响应、错误、耗时和 token usage，这些日志可以帮助我们分析模型什么时候选择工具、工具参数是否合理、上下文压缩是否有效。

## 第 4 页：详细需求描述

建议用时：1 分钟 10 秒

### PPT 展示文字

- 基础交互：`mini-code chat`
- 工具能力：`bash`、读文件、写文件、编辑文件
- 状态能力：Todo、任务板、会话记录、后台任务
- 智能能力：工具调用、子代理、技能加载、自动压缩
- 协作能力：生成队友、消息收件箱、任务认领、关停协议
- 配置能力：环境变量、`.env`、模型 ID、Anthropic Base URL

### 讲稿

从项目内容来看，需求可以分成六类。

第一类是基础交互需求。系统需要提供一个 CLI 入口，让用户可以通过 `mini-code chat` 开始会话，也可以通过 `tasks`、`team`、`bg` 等子命令查看任务、团队和后台任务状态。

第二类是工具能力需求。模型需要能够读取项目文件、写入文件、执行 shell 命令、编辑文件内容。否则模型只能给出建议，不能真正参与开发流程。

第三类是状态管理需求。复杂任务不是一轮完成的，所以系统需要 Todo 列表、持久任务板、会话快照和后台任务记录。这些状态都保存在工作区本地目录中，例如 `.tasks`、`.team`、`.sessions` 和 `.transcripts`。

第四类是智能能力需求。模型要能够根据当前任务选择工具，还要支持上下文过长时的自动压缩，也要能通过 `load_skill` 加载特定技能说明，通过 `task` 工具启动子代理完成隔离探索。

第五类是协作需求。项目支持生成 teammate，每个队友有自己的角色、线程和工具集合。队友可以接收消息、发送消息、认领任务，也可以通过 shutdown 协议退出。

第六类是配置需求。系统需要从环境变量或 `.env` 加载模型 ID、API Key、Base URL 等配置，并统一生成工作区路径，保证运行环境可复现。

## 第 5 页：概要设计

建议用时：1 分钟

### PPT 展示文字

- 架构分层：
  - `cli`：命令行入口
  - `runtime`：代理主循环和工具调度
  - `features/tools`：业务能力与工具执行
  - `llm/config`：模型调用与配置
- 依赖方向：CLI -> Runtime -> Features/Tools/LLM
- 状态目录：`.tasks`、`.team`、`.sessions`、`.transcripts`、`.logs`

### 讲稿

项目的概要设计采用分层结构。

最上层是 `cli.py`，负责解析命令行参数、进入交互式会话，以及把运行结果打印给用户。它本身不直接处理复杂逻辑，而是通过 `build_app()` 组装配置、模型 provider、各类 manager 和 runtime。

中间层是 `runtime.py`，这是整个项目的核心。它负责维护对话历史、构建工具 schema、调用模型、解析模型返回的 tool use，并把工具执行结果重新注入到历史中。

再往下是 `features` 和 `tools`。`features` 包含任务板、Todo、技能加载、后台任务、团队协作等业务能力；`tools` 包含文件读写、编辑、shell 执行和子代理运行。

底层是 `llm.py` 和 `config.py`。`llm.py` 封装 Anthropic 调用和日志记录，`config.py` 负责环境变量、工作区路径和运行阈值。

这样的依赖方向比较清晰：CLI 依赖 Runtime，Runtime 依赖 Features、Tools 和 LLM，而 Tools 不反向依赖 Runtime。这降低了模块耦合，也让单元测试更容易编写。

## 第 6 页：解决方案详细设计

建议用时：1 分钟 15 秒

### PPT 展示文字

- `AgentRuntime.run_turn()`：
  1. 压缩旧工具结果
  2. 注入后台结果和团队 inbox
  3. 构建系统提示词和工具 schema
  4. 调用模型
  5. 执行模型请求的工具
  6. 将工具结果回注入历史
- 支持自动压缩和手动 `/compact`

### 讲稿

详细方案的核心是 `AgentRuntime.run_turn()`。它定义了一轮代理工作的完整生命周期。

第一步是上下文处理。系统会先执行 `microcompact`，把较早且较长的工具结果替换成简短标记，保留最近几次工具结果。这样可以减少无效上下文占用。如果整体历史超过阈值，还会触发 `auto_compact`，调用模型对历史进行总结，并把总结作为新的延续上下文。

第二步是外部事件注入。后台命令完成后，结果会以 `<background-results>` 的形式注入历史。团队消息则会以 `<inbox>` 的形式注入历史。这样模型在下一轮就能感知异步任务和队友消息。

第三步是模型调用。Runtime 会构建系统提示词和工具 schema，然后通过 provider 调用模型。这里的工具 schema 描述了模型可用的工具名称、参数类型和必填字段。

第四步是工具调度。如果模型返回 `tool_use`，Runtime 会根据工具名找到对应 handler，比如 `read_file`、`bash`、`task_create` 或 `spawn_teammate`。工具执行后，系统把结果包装成 `tool_result`，继续交给模型。

因此，模型负责选择动作，系统负责真实执行和结果反馈。这个设计形成了“模型推理 - 工具执行 - 结果回传 - 继续推理”的闭环。

## 第 7 页：模型使用方式

建议用时：1 分钟 10 秒

### PPT 展示文字

- 当前模型提供方：Anthropic
- 调用封装：`AnthropicProvider.create_message()`
- 模型输入：
  - system prompt
  - conversation history
  - tool schemas
  - max_tokens
- 模型输出：
  - text：直接回复
  - tool_use：触发真实工具执行
- 结构化日志：记录 request、response、error、duration、usage

### 讲稿

项目中模型的使用方式比较集中，主要通过 `AnthropicProvider.create_message()` 完成。这样做的好处是所有模型调用都走同一个入口，便于统一配置、统一记录日志，也便于后续替换实现。

每次模型调用的输入主要包含四部分。第一是 system prompt，用来告诉模型当前工作区、可用技能和行为规范。第二是 conversation history，也就是用户输入、模型回复和工具结果组成的历史。第三是 tool schemas，用来告诉模型有哪些工具、每个工具需要哪些参数。第四是 `max_tokens`，限制单次输出规模。

模型输出也分两类。一类是普通文本，说明模型认为可以直接回复用户。另一类是 `tool_use`，说明模型希望系统执行某个工具。例如模型可能请求 `read_file` 来查看文件，请求 `bash` 来运行测试，或者请求 `task_create` 创建任务。

另外，项目对模型调用做了结构化日志记录。每次交互都会记录 request、response、error、duration 和 usage。并且日志会对重复前缀做压缩，只保留和上一次不同的部分，降低日志体积。这对分析模型行为非常重要，因为我们可以回看模型在每一步看到的上下文，以及它为什么选择某个工具。

## 第 8 页：模型能力分析

建议用时：1 分钟 20 秒

### PPT 展示文字

- 已利用能力：
  - 任务理解与步骤规划
  - 工具选择与参数生成
  - 代码阅读和修改建议
  - 长上下文总结
  - 多代理任务拆分
- 能力边界：
  - 工具执行必须由系统兜底
  - 上下文压缩可能丢失细节
  - 复杂协作依赖明确协议
  - 模型错误需通过测试和日志发现

### 讲稿

从本项目来看，模型主要发挥了五类能力。

第一是任务理解能力。用户输入通常是自然语言，模型需要从中判断目标、约束和下一步行动。例如用户要求修改功能时，模型要先判断应该阅读哪些文件，而不是直接猜测代码。

第二是规划能力。复杂任务需要被拆成多个步骤，比如读取项目结构、定位模块、修改代码、运行测试、根据结果继续修复。项目中的 Todo、任务板和子代理工具都可以承接这种规划能力。

第三是工具选择能力。模型看到工具 schema 后，需要判断什么时候调用 `bash`，什么时候调用 `read_file`，什么时候更新任务状态。这是编码代理区别于普通聊天机器人的关键能力。

第四是上下文总结能力。当对话历史过长时，`auto_compact` 会要求模型总结任务概况、当前状态、关键决策、下一步和需要保留的上下文。这个能力让长期任务可以继续推进。

第五是协作能力。对于 teammate 和 subagent，模型可以被赋予不同角色，并围绕指定 prompt 工作。这说明模型可以在一定程度上承担角色化任务分工。

但模型也有明显边界。它不能被完全信任去直接操作系统，所以路径安全、危险命令拦截、输出截断必须由代码实现。模型也可能选错工具、生成错误参数，或者在上下文压缩时遗漏细节。因此项目通过工具 handler、日志、transcript 和单元测试来兜底。总体来看，模型适合负责理解、规划和决策，而系统必须负责执行、安全和验证。

## 第 9 页：验证方法和结果

建议用时：55 秒

### PPT 展示文字

- 验证方法：
  - 单元测试覆盖配置、CLI、Runtime、LLM、工具、任务、团队、后台
  - Fake Provider 模拟模型响应
  - 验证 tool_use、压缩、日志、inbox、任务依赖
- 当前结果：
  - `pytest -q`
  - 52 个测试全部通过
  - 运行结果：`52 passed in 0.28s`

### 讲稿

项目验证主要采用自动化单元测试。

这里有一个关键点：测试没有依赖真实模型。因为真实模型输出存在不确定性，如果直接调用真实模型，很难稳定判断测试是否通过。项目使用 Fake Provider 模拟模型响应，比如模拟模型返回文本，或者模拟模型返回 `tool_use`。这样就可以稳定测试 Runtime 的行为。

测试覆盖了多个方面：配置加载、CLI 子命令、文件工具、任务创建和依赖解除、团队消息发送和读取、后台结果注入、手动压缩、自动压缩、LLM 结构化日志等。

我实际运行了 `pytest -q`，当前结果是 52 个测试全部通过，用时 0.28 秒。这说明项目的核心模块和关键流程已经通过了可重复验证。

## 第 10 页：应用效果与总结

建议用时：1 分钟 20 秒

### PPT 展示文字

- 应用效果：
  - 形成可运行的 mini 编码代理
  - 支持本地工作区状态持久化
  - 支持复杂任务拆分和多代理协作
  - 支持模型调用可观测与可分析
- 总结：
  - 模型负责理解、规划和决策
  - 系统负责工具、安全、状态和验证
  - 二者结合才构成可靠编码代理

### 讲稿

从应用效果看，mini_code 已经形成了一个可运行的编码代理基础框架。用户可以通过 CLI 输入开发任务，模型可以根据上下文选择工具，系统执行工具后再把结果反馈给模型。

在状态管理方面，项目把任务、团队、会话、日志和 transcript 都保存在工作区目录中。这意味着任务可以被持续跟踪，模型调用可以被回溯，后台和队友消息也可以进入后续对话。

在协作方面，项目支持子代理和 teammate。子代理适合隔离探索，比如只读文件、总结信息；teammate 则更接近持久协作者，可以处于 working、idle 或 shutdown 状态，并通过消息总线参与团队任务。

本项目最大的结论是：大模型本身能力很强，但可靠的编码代理不能只依赖模型。模型更适合承担理解、规划、生成和决策；系统代码则必须承担工具执行、安全限制、状态保存、日志记录和测试验证。只有把两者结合起来，才能让模型能力真正进入工程流程。

后续如果继续扩展，可以考虑增加更多模型 provider、加强权限审批、完善长期会话恢复，并对真实模型调用日志做统计分析，例如工具调用成功率、压缩前后信息保留情况，以及不同任务类型下模型的表现差异。

参考实现主要集中在 `src/mini_code/runtime.py`、`src/mini_code/llm.py`、`src/mini_code/features/team.py` 和 `docs/architecture.md`。
